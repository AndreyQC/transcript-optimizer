## 1. Суть идеи

Две части.

**(а) Промпт-задание** (внешний документ, приложен пользователем): десктоп-приложение
транскрибации видеофайлов со встреч, полностью локальное, CPU-only (32 ГБ ОЗУ, без GPU).
Пайплайн: выбор видео → ffmpeg (16 кГц mono WAV) → ASR (`rlx-whisper` или
`transcribe-rs`, с `initial_prompt`) → диаризация (`polyvoice`) → сшивка по таймкодам →
словарь замен → редактируемый транскрипт. Плюс: пресеты-промпты в JSON, повторное
применение замен без перетранскрибации, post-processing hooks (`YandexMessengerHook` —
заглушка), одностраничный UI без тяжёлых библиотек.

**(б) Добавление пользователя:** Rust-агент, который в интерактивном виде помогает
править словари (в промпт-задании его нет — это расширение идеи).

|---|---|---|---|---|
| `rlx-whisper` | да | 0.2.11 | **GPL-3.0-only** | Pure-Rust Whisper (экосистема RLX), без whisper.cpp-биндингов; молодой (первая публикация 2026-05-28), min Rust 1.87 |
| `transcribe-rs` | да | 0.3.12 | MIT | Multi-engine STT (Parakeet, Moonshine, SenseVoice, GigaAM, Whisper GGML/ONNX); ~280K загрузок, обновлялся 2026-10-02; Whisper-движки поверх `whisper-rs` |
| `polyvoice` | да | 1.0.0 | MIT | CPU-only диаризация: самописные INT8-ядра, пара моделей ~8.4 МБ, DER ~11.3%; offline и streaming; default features пустые (ort-free) |

Ссылки: [crates.io/rlx-whisper](https://crates.io/crates/rlx-whisper),
[crates.io/transcribe-rs](https://crates.io/crates/transcribe-rs),
[crates.io/polyvoice](https://crates.io/crates/polyvoice),
[github.com/ekhodzitsky/polyvoice](https://github.com/ekhodzitsky/polyvoice).

**Вывод:** связка реальна и собираема на CPU. Критичные оговорки:

- **`rlx-whisper` под GPL-3.0-only** — для личного инструмента терпимо, но делает
  приложение GPL-заражённым при любой публикации/распространении. Плюс крейт молодой
  (0.2.x). Фактически сужает выбор до `transcribe-rs` (MIT).
- **Скорость на CPU.** Whisper medium/large на CPU без GPU — порядка единиц realtime;
  часовая встреча считается десятками минут. Замеры обязательны (спайк, §9).
- **`polyvoice` 1.0.0** вышел 2026-10-01 — версии считанные дни. DER 11% — спикеры
  будут путаться на пересечениях; ручная правка результата обязательна (у нас для этого
  уже есть UX). Альтернатива на будущее: `speakrs` (заявлен DER 7.1%).

## 3. Пересечение с существующим transcript-optimizer

| Блок идеи | Статус в проекте |
|---|---|
| Словарь замен `from → to` + применение к транскрипту | **ЕСТЬ** — `app/src/engine/rules.ts` (нормализация, многословные фразы, OOV), YAML + CST-редактор `app/src/lib/yaml-edit.ts`, Monaco |
| Редактируемый транскрипт + повторное применение замен | **ЕСТЬ** — это ядро текущего приложения |
| Fuzzy-поиск похожих `from`, дедуп по `to` | **ЕСТЬ** — `app/src/lib/similarity.ts`, кнопка дедупа (LESSONS §§7–8) |
| Пресеты: `initial_prompt` + replacements в одном наборе | **ЧАСТИЧНО** — replacements.yaml есть; `initial_prompt` — новая сущность |
| Пайплайн ffmpeg → ASR → диаризация → сшивка | **НЕТ** — единственный принципиально новый блок |
| Прогресс по стадиям, события в UI | **НЕТ** (типовая механика `app.emit`) |
| Post-processing hooks | **НЕТ**; `YandexMessengerHook` — заглушка с логированием |
| UI-скаффолд (FilePicker, PresetSelector, …) | Дублирует существующий `app/src/` |

**Вывод:** около половины функциональности идеи (вся пост-обработка и словарная часть)
уже реализована и обкатана в transcript-optimizer. Принципиально новое — только
upstream-пайплайн распознавания, пресеты-промпты и хуки. Строить «полный проект с нуля»
по промпту — значит дублировать самую зрелую часть кодовой базы.

## 4. Ключевой вопрос: отдельное приложение или расширение

| Вариант | Плюсы | Минусы |
|---|---|---|
| (а) Новое приложение с нуля (как в промпте) | Изоляция рисков; чистый скаффолд под задачу | Дублирование словарного стека, движка замен, Monaco/YAML-редакторов; двойная поддержка |
| (б) Модуль в существующем `app/src-tauri` | Максимум переиспользования; один продукт | Тяжёлые ML-зависимости (whisper.cpp toolchain: cmake/clang; ONNX) удлиняют сборку основного приложения |
| (в) Sidecar-бинарь-пайплайн + UI в существующем приложении | ML-депенденси изолированы в одном крейте; бинарь пригоден headless во внешнем пайплайне (в стиле `replacements.compact.txt` из Phase 9); UI и словари — существующие | Чуть больше склейки (spawn + stdio-JSON или Tauri-команда-обёртка) |

## 5. Rust-агент для интерактивной правки словарей

Что уже есть в приложении: OOV-грид с добавлением в словарь из контекста
(`ContextActionDialog`), fuzzy-детект похожих `from` (Левенштейн, `similarity.ts`),
дедуп по `to`. «Агентом» этого не делает только отсутствие **пакетного интерактивного
цикла**: прошёл по транскрипту → собрал кандидатов → предложил пачкой → принял
решения → применил одним diff-превью.

Варианты формы:

- **CLI REPL** (отдельный cargo-bin): работает headless, но дублирует UX правки словарей
  и лишён Monaco/diff-превью.
- **In-app proposal engine** (рекомендуется): Rust-команда
  `suggest_dictionary_edits(transcript, dict) -> Vec<Proposal>` — кандидаты из OOV +
  частотностей + fuzzy-матчей к существующим `from` (переиспользуем `norm`/`tokenize`
  из движка, паттерн из LESSONS §6); UI — чеклист предложений; применения — через
  существующий CST-стек `yaml-edit.ts` с обычным `pending`/Превью/Применить.
  Опционально: LLM-подсказка «какой `to` предложить» через существующий
  `app/src/store/llm.ts` (OpenAI-совместимый стрим уже есть).

Агент НЕ пишет в словарь сам: решения всегда за пользователем, применения идут через
diff-превью (урок §8 LESSONS: мульти-строчные операции — только через превью).

## 6. Открытые вопросы

### Q1. Куда строим: (а) новое приложение / (б) модуль / (в) sidecar + существующий UI?

**Рекомендация ИИ: (в).** Пайплайн — отдельным workspace-крейтом (sidecar-бинарь),
UI-обвязка и словарная часть — в существующем приложении. Так ML-зависимости не
отравляют сборку основного продукта, а бинарь встаёт во внешний пайплайн пользователя
как и `replacements.compact.txt`. Если сборка (б) окажется не больной — (в) легко
схлопывается в (б).

> `USER_INPUT 1:` ...

### Q2. ASR-крейт: `rlx-whisper` или `transcribe-rs`?

**Рекомендация ИИ: `transcribe-rs`.** MIT, активная разработка, несколько движков
(если Whisper на CPU окажется медленным — есть Parakeet/Moonshine как кандидаты на
сравнение в спайке). `rlx-whisper` отвергаем из-за GPL-3.0-only и молодости; к нему
можно вернуться, если чистый Rust без whisper.cpp станет принципиален.

> `USER_INPUT 2:` ...

### Q3. Формат пресетов: JSON из промпта или YAML?

**Рекомендация ИИ: YAML, по образцу существующих словарей.** Один формат на проект:
переиспользуем валидацию, CST-редактор, Monaco-подсветку. Пресет = новый вид записи
(`initial_prompt` + ссылки на replacements), а не параллельная JSON-сущность в
`app_data_dir`. Подлежит проработке в плане фазы.

### Q4. Форма агента: CLI REPL или in-app proposal engine?

**Рекомендация ИИ: in-app proposal engine** (§5): Rust считает предложения, UI
показывает чеклист, применения — через существующий diff-превью; LLM — опция. CLI
оставляем вне MVP.

## 7. Риски и подводные камни

- **Время на CPU.** Часовая встреча на Whisper-medium — десятки минут; нужен
  прогресс по стадиям, отмена, невыделяющийся главный поток (`spawn_blocking`,
  урок: не блокировать UI). Замеры — первым спайком, до выбора модели.
- **Качество диаризации.** DER ~11% у polyvoice: пересечения спикеров и одновременная
  речь будут путаться; ручная правка обязательна — благо редактор уже есть.
- **ffmpeg.** Внешний бинарь: требование «в PATH» или bundling в установщик — решить
  в плане фазы.
- **Модели GGML/ONNX.** Первый запуск должен скачать ~0.5–1.5 ГБ; место хранения
  (`app_data_dir`) и обработка офлайна.
- **Toolchain сборки.** `whisper-rs` тянет whisper.cpp (cmake/clang) — на Windows
  требует подготовки окружения; ещё один аргумент за изоляцию пайплайна (Q1-в).
- **Сшивка спикеров.** Пересечение таймкодов — эвристика; на сегментах с двумя
  спикерами в одном интервале нужен детерминированный тай-брейк (максимальное
  пересечение), и это надо покрыть тестами.

## 8. Сводная рекомендация

Идея реализуема на заявленном стеке (все три крейта существуют, два из трёх — MIT).
Строить отдельное приложение с нуля нецелесообразно: словарно-постобработочная половина
идеи уже есть в transcript-optimizer. Рекомендованный контур: sidecar-крейт
пайплайна (ffmpeg → transcribe-rs → polyvoice → сшивка) + интеграция в существующее
приложение (пресеты-YAML, прогресс, редактор) + in-app Rust-агент предложений по
словарю. Первое действие после закрытия Q1–Q4 — минимальный спайк пайплайна на
одном реальном видео с замерами времени и качества.
