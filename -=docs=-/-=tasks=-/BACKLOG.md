# Бэклог будущих задач

Идеи и отложенные работы — то, что **осознанно не делаем сейчас**, но стоит
вернуться, когда станет актуально. Источник записей — в основном разделы
«Что НЕ делаем (осознанно)» и «Риски и нюансы» в планах `-=tasks=-/<date>/`.

---

## Назначение и правила

- **Один источник отложенных задач.** Когда в плане фичи появляется пункт
  «не делаем сейчас — отдельной задачей» или риск с пометкой «рассмотреть
  позже» — он переносится сюда короткой записью со ссылкой-источником.
- **Не дублируем детали.** Здесь — суть (что, зачем, когда стало актуальным),
  указатель на план/чекпоинт/урок, где проблема разобрана подробно.
- **Приоритет и статус** — опциональны, проставляются по мере прояснения.
- **Закрытые записи НЕ удаляются** — помечаются `~~зачёркнутым~~` со ссылкой на
  реализовавший план/фазу (история для будущих сессий).
- **Не место для срочного.** То, что нужно сделать в текущей фазе, живёт в её
  плане; здесь — только то, что сознательно отложено за рамки.

Формат записи:

```
### [Короткое название]
**Суть:** одна-две строки — что сделать.
**Контекст:** ссылка на план/урок/чекпоинт (относительный путь + §раздел).
**Зачем:** почему это когда-нибудь понадобится / какая проблема закроется.
**Оценка сложности:** S/M/L/XL (грубая) — опционально.
```

## Активные записи

### Компакт-справочник: порезка по релевантности транскрипта

**Суть:** при генерации саммари включать в блок автозамен (промпт + файл
`replacements.compact.txt`) **только те правила**, чьи `from`/`from_lemmas`
встречаются в текущем транскрипте, а не весь `replacements.yaml` целиком.

**Контекст:**
- `-=tasks=-/2026-07-27/20260727_001_compact_replacements_in_prompt_plan.md`
  §9 «Риски и нюансы» — пункт «Размер промпта».
- `LESSONS_LEARNED.md` §6 — там же паттерн «собрать вхождения многословных фраз
  в репликах» (`Map<lineNo, [{start,end}]>`); его можно переиспользовать для
  матчинга `from` по тексту.
- `app/src/engine/rules.ts` — `buildReplaceIndices` + `norm()` из
  `engine/tokenizer.ts` (тот же `tokenize`/`wordBoundaryRe`, чтобы границы
  слов на кириллице совпадали).

**Зачем:**
- На текущем sample (~80 правил, ~3-5 КБ) весь справочник влезает в промпт
  без боли. Но словарь растёт — и каждый запуск саммари начнёт платить
  токенами за правила, которые в данном транскрипте **вообще не
  встречаются**. Это и дороже, и шумнее для модели.
- Для пайплайна (файл `replacements.compact.txt`) релевантность ещё важнее:
  файл пишется один раз на весь `replacements.yaml`, а читается для
  конкретного транскрипта — хотелось бы уметь сузить.

**Подводные камни (к чему быть готовым при проработке):**
- **Многословные `from`** (`English Club`, `опен код`) — матчить подстрокой
  через `wordBoundaryRe`, как движок; обычный `String.includes` даст
  ложные матчи на границах слов.
- **Регистрочувствительность.** Движок нормализует `from` через `norm()`
  (lowercase + схема пробелов). Фильтрация должна использовать ту же норму,
  иначе `Excel` vs `excel` разойдутся.
- **Леммы** (`from_lemmas`) — движок лемм сейчас в MVP не применяется
  (см. `20260722_001_checkpoint.md` §«Known gaps»). Если к моменту проработки
  движок лемм появится — фильтровать и их по той же логике.
- **Пороги.** Правило с единичным вхождением `from` в транскрипте — включать
  или нет? Гипотеза: включать (модель должна знать каноническую форму даже
  для одного случая). Но если словарь большой, а транскрипт короткий —
  выгода от фильтра падает. Возможен настраиваемый порог.
- **Отдельный артефакт или опция?** Два варианта:
  (а) новый файл `replacements.compact.<hash>.txt` per-транскрипт —
  усложняет пайплайн;
  (б) фильтрация только в промпте саммари (in-memory), файл остаётся
  полным — проще, но пайплайн не получает выгоду.
  Решение принять при проработке.

**Оценка сложности:** M (есть готовый паттерн матчинга в `rules.ts`, но
требует решения по порогам и формату артефакта).
